PAYWALL
- Never show automatically on first app launch or during onboarding.
- Preserve and verify the previously approved upgrade-moment timing and eligibility rules. Do not invent new timing rules.

PURCHASE AND RESTORE
- Use existing native Apple purchase infrastructure.
- Verify purchases and account ownership through the backend before confirming Pro access.
- Prevent stale asynchronous results from changing another signed-in account's UI state.

- Never report restore success unless a valid entitlement is confirmed.
- Preserve existing free-user functionality.
- Pro access must reflect canonical server entitlement status.

MEMBERSHIP
- Settings shows the verified membership state, selected plan, trial/renewal/expiry dates and appropriate management actions.
- Handle Free, Trial, Active, Grace, Cancelled-but-entitled, Expired and Unknown states truthfully.

CANCELLATION
- User selects Cancel subscription in Settings.
- Show a reason screen with Jamie's five options:

  4. Technical problem

- Continue to Apple's subscription management.
- Collect cancellation feedback privately.
- Do not equate feedback submission, opening Apple's settings or disabling renewal with confirmed cancellation.
- Refresh canonical provider status when the user returns.
- Show a calm, accurate end-date confirmation only when supported by verified provider state.
- Record feedback and verified cancellation outcome separately.

DEPENDENCIES

### Data/API design proposed for approval

Keep GET /api/native-subscriptions/status compatible and canonical. Add GET /api/native-subscriptions/membership for owned current/historical plan/provider/state/dates plus canonical summary and evidence status; never infer Free from missing detail. Add POST /api/native-subscriptions/reconcile with a validated owned subscription ID: fetch provider state, verify it, persist an accepted snapshot and return fresh membership. Rate-limit and deduplicate per owner/subscription; use bounded provider requests, no continuous polling. Reconciliation is read-only at the provider, but writes verified state locally after implementation/deployment approval.
Add POST /api/native-subscriptions/cancellation-feedback with client intent UUID, owned subscription ID, enum reason and bounded Other text. Proposed Other limit: 1-1000 trimmed characters; other reasons store empty details. Derive owner from bearer auth, never client user ID. Same ID/same payload retries return existing success; same ID/different payload is an explicit conflict, never silent success. Lock the submitted answer per intent in UI after first attempt; allow retry, Back and continue-without-feedback even after timeout/save failure.

Proposed new tables (names fixed for plan):
- subscription_cancellation_feedback: owner FK, subscription FK, intent UUID, reason, optional details, submitted_at; unique(owner,intent). Private server-mediated access; no direct anon/authenticated reads/writes. Service-role API still checks owner and subscription. Do not log/export free text to analytics.
- subscription_trial_history: immutable provider trial episode key, owner/subscription/environment, verified start/end, verification metadata. Unique(provider,environment,episode). Start/end come from verified provider fields, not restore time, created_at or inferred seven-day subtraction. Restore/renewal cannot create a new episode for the same trial. Unknown historical dates remain unknown; no blanket backfill.
- subscription_lifecycle_evidence: append-only minimal provider event/evidence type, provider event ID, owner/subscription/environment, effective/verified times and accepted snapshot fingerprint. No raw receipt/token/payload. Separate from feedback; unique provider evidence identity. Membership only projects evidence valid for the current accepted snapshot; terminal/reactivation state takes precedence.
All new tables enable RLS with direct client privileges revoked; service-only functions use fixed search_path, role checks and qualified tables. Ownership constrained through subscription/owner consistency and API checks; delete dependent private records on account deletion using FK cascades. No changes to existing RLS/access policies. Retention duration/operator access policy must be confirmed before production; do not add an admin viewer in M3-01.

Atomicity: add a narrowly scoped wrapper around existing upsert_subscription_entitlement. Acquire existing per-user advisory lock; validate owner, compare incoming ordering to the stored snapshot, call existing upsert and insert evidence/trial facts only for the accepted revision in the same transaction. Stale/duplicate snapshots create no new current confirmation; evidence failure rolls back snapshot acceptance. Reuse provider event claims. Old writers keep existing signature; any newer snapshot without matching evidence makes old confirmation inapplicable. No auto_renews=false trigger/backfill. Tests must cover competing transactions, identical timestamps, replay and injected rollback.
Apple: explicit verified DID_CHANGE_RENEWAL_STATUS/AUTO_RENEW_DISABLED is cancellation evidence, not a generic false flag. Bind evidence to matching verified transaction/renewal identity, product, environment and accepted state; missing signing time fails safely. Verified reactivation/revocation/expiry supersedes old messages. Reconciliation can refresh status but an off flag without explicit event evidence stays unknown for cancellation confirmation. Do not promise synchronous confirmation if Apple notification has not arrived.
Stripe: retain existing management and canonical access. Use freshly retrieved provider cancel_at_period_end/cancel_at intent with provider-specific wording (scheduled to end), never infer why it ended from status=canceled or auto_renews=false. Record explicit schedule/reactivation evidence with the accepted snapshot; do not label refund/terminal defaults as user cancellation. Google remains deferred; shared storage must not infer Google confirmations.
Apple current-state reconciliation uses existing installed AppStoreServerAPIClient/getAllSubscriptionStatuses plus verification of returned signed transaction/renewal data. New server-only key ID, issuer ID and signing key are required if not already provisioned. No keys requested in chat. If unavailable, return saved canonical state plus reconciliation pending/error; do not fabricate current provider confirmation. Do not grant access from client claims or weaken existing ownership rules.
